# Bunko — Testing Strategy

Playwright is the single test framework across the stack — for API/
integration tests (via Playwright's `request` fixture, no browser
needed) and for browser E2E tests. One framework, one config format,
one report, one CI step type.

## 1. Test Types

| Type | Where | Tool | Runs |
|---|---|---|---|
| API/integration | `backend/tests/` | Playwright Test (`request` fixture against a running server + test DB) | Every PR |
| Browser E2E | `frontend/e2e/` | Playwright Test (`page` fixture, real browser) | Every PR (critical journeys), nightly (full suite) |
| Manual exploratory | — | — | Before major releases |

There is no separate unit-test runner (no Jest/Vitest). Pure functions
and isolated business logic are still tested — as small, focused
Playwright API tests that exercise the service through its route,
rather than importing the function directly. This keeps one mental
model and one config for every contributor and agent. If a piece of
logic is awkward to reach via an API test, that's usually a sign it
should be exposed as its own endpoint or extracted with a clearer
seam — flag it rather than reaching for a second test tool.

## 3. What Must Be Tested Per Module

### `auth`
- Register: duplicate email rejected, password policy enforced,
  password never returned in response.
- Login: wrong password rejected, token issued on success.
- Refresh: rotated token invalidates the old one.

### `library` / `editions` / `copies`
- A work cannot be added twice to the same user's library (or is
  idempotent — pick one behaviour and test it).
- A user cannot fetch/modify another user's work (403/404 boundary).

### `reading-sessions` (SRS §12 — highest-risk module for edge cases)
- Starting a session while one is already `ACTIVE` returns 409.
- Idle timeout transitions `ACTIVE` → `PAUSED` after the configured
  threshold. Use a test-only endpoint or injectable clock to advance
  time deterministically — Playwright tests must not `page.waitFor`/
  sleep for real minutes.
- Reopening within the grace window resumes the same session; beyond
  it, ends the paused session automatically (SRS §12.8 step 5).
- `end` is idempotent: calling twice with the same payload returns
  the same result without erroring.
- Physical session requires `endPosition` before it can end (SRS
  §12.9 step 4).

### `continuity` (SRS §11 — the core differentiator, test thoroughly)
- Structural ID match returns confidence in the high band and skips
  later steps.
- Title-match fallback triggers only when structural ID match fails.
- Below-threshold confidence returns `requiresConfirmation: true`
  and does NOT auto-navigate.
- The worked example from `SRS.md` §11.9 is encoded as a literal spec
  case — if this test breaks, the algorithm's behaviour changed.

### `files`
- Upload rejected if declared size exceeds remaining quota.
- Confirm step rejects a file whose actual content doesn't match its
  declared MIME type (e.g. an executable renamed to `.epub`).
- Signed URLs are time-limited and cannot be reused after expiry
  (test the expiry parameter is set, not necessarily that S3 enforces
  it — that's AWS's contract, not ours).

## 4. Test Data

- Use factory functions (`backend/tests/fixtures/`), not fixtures
  checked into version control with real book content.
- Never use actual copyrighted book text in test fixtures — use short
  Lorem-ipsum-style placeholder EPUB/PDF files generated by
  `generate-sample-epub.ts`.
- Each spec file gets a fresh, isolated user via the `auth.fixture.ts`
  helper — tests must not depend on execution order or shared state.

## 5. Coverage Expectations

- No hard line-coverage percentage gate (a poor proxy for quality) —
  instead, every PR's Definition of Done requires tests for the
  acceptance criteria listed in its ticket (`TASKS.md`).
- `continuity` and `reading-sessions` specs are the exception: every
  branch listed in §3 above must have an explicit test case, checked
  in code review, not just aggregate coverage.

## 6. Swagger/OpenAPI as a Contract Test

Because `docs/openapi.yaml` is the binding API contract
(`AGENTS.md` §1), a dedicated spec (`backend/tests/openapi.spec.ts`)
validates that every response in the API test suite matches its
declared schema in `openapi.yaml` (via a lightweight schema-validation
assertion helper). This catches drift between the spec and the actual
implementation automatically, rather than relying on manual review.

## 7. CI Gates (`.github/workflows/ci.yml`)

Every PR must pass, in order:

1. `npm run lint` (backend and frontend)
2. `npm run typecheck` (backend and frontend)
3. `npm run test` — Playwright API suite (backend), against an
   ephemeral Postgres + Redis + MinIO (via Docker Compose in CI)
4. `npm run test:e2e` — Playwright browser suite (frontend), critical
   journeys only; full suite runs nightly against staging

A PR cannot merge with any step failing or skipped.
